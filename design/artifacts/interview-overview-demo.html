Spoken answers

  1. To start, please tell us a bit about yourself and walk us through your professional experience, especially with Python and PostgreSQL.

    8/10

    Answer I have been working with Python for about eight years, mostly FastAPI and data pipelines. The last three years were PostgreSQL 14/15 in fintech: partitions, EXPLAIN, and PL/pgSQL for balance checks. I keep business logic in the application and put in the database only what has to sit next to the data.

    Opinion Clear, structured intro with relevant Python and PostgreSQL depth for a senior funds-platform role. No fluff, good seniority signal.

    • Could name team size and ownership of production incidents more explicitly.

  2. What drew you to this Senior Python Developer role at CodeTalent, on a large project for a leader in investment-fund distribution?

    8/10

    Answer I want a larger project with a real funds model, not another CRUD service. Hybrid work and a team that talks seriously about PostgreSQL and GCP matches what I already do. I would rather work closer to NAV, holdings, and reporting than only ETL.

    Opinion Motivation is specific to the offer (funds, PostgreSQL, hybrid) rather than generic growth. Good fit signal.

  3. How do you read EXPLAIN ANALYZE, and how do you tell a bad plan from bad statistics, for example with a nested loop, hash join, or bitmap scan?

    9/10

    Answer I compare actual rows with the estimate. If the estimate is orders of magnitude off, I run ANALYZE and look at extended stats before adding an index. Nested loop with thousands of iterations on a bad estimate is the classic case. Hash join spilling to disk is work_mem or a poor hash key.

    Opinion Correct mental model: stats versus access path, with named node types. Senior-level diagnosis.

  4. When would you move logic into PL/pgSQL instead of keeping it in Python, and what risks come with VOLATILE, STABLE, IMMUTABLE, and SECURITY DEFINER functions?

    8/10

    Answer I put in the database what must be atomic with the data: balance checks, numbering, constraint-like rules. VOLATILE blocks inlining; IMMUTABLE on a function that calls now() is a classic bug. SECURITY DEFINER only with a fixed search_path and a non-superuser owner.

    Opinion Knows volatility and definer risks, not just syntax. Right split between app and database.

  5. How do you choose PostgreSQL transaction isolation levels for financial operations, and how would you diagnose anomalies such as phantom reads, write skew, or deadlocks at scale?

    9/10

    Answer Default is READ COMMITTED. For read-modify-write on holdings I use REPEATABLE READ or SELECT FOR UPDATE. Phantoms mean the range was not locked. Write skew I catch with serializable or an explicit lock. Deadlocks: timeout, retry, a fixed lock order, and log_lock_waits.

    Opinion Maps isolation levels to real financial anomalies. Retry and lock-order discipline is what we want in production.

  6. How do you build a production Docker image for a Python app that talks to PostgreSQL so it stays small, repeatable, and safe?

    8/10

    Answer Multi-stage: builder with pip, runtime on slim or distroless. Layers are system packages, requirements, then code. I pin image digests and requirements. Non-root, no secrets in the image env, migrations as a job not a forever entrypoint.

    Opinion Covers size, reproducibility, and secrets. Practical production answer.

  7. How do you design B-tree, partial, covering (INCLUDE), GIN, and BRIN indexes for specific queries, and how do you know an index has started to hurt writes?

    8/10

    Answer B-tree for equality and range. Partial when most rows are inactive. INCLUDE to avoid a heap fetch. GIN for JSONB and arrays. BRIN for append-only NAV history. Harm shows up in idx_scan versus inserts and in INSERT time.

    Opinion Workload-matched index types plus a write-cost signal. Strong practical skills answer.

  8. How would you model data for a fund-distribution platform — instruments, portfolios, holdings, NAV history, and corporate actions — balancing normalization with fast reporting?

    8/10

    Answer Canonical 3NF: instrument, share class, portfolio, holding with effective_from/to. NAV time series stored separately, partitioned by date. Corporate actions as an event log, not a mutation of history.

    Opinion Separates system of record from reporting and treats corporate actions as events. Right architecture for funds data.

  9. How would you design region and database failure resilience on GCP, defining RPO and RTO for a funds platform and proving them in practice?

    8/10

    Answer RPO near zero for holdings bookkeeping: Cloud SQL HA in-region plus PITR. RTO in minutes, not hours. Cross-region is async replica or backup, with lag called out. Quarterly game day: failover, restore to a timestamp, check the NAV job.

    Opinion Quantifies RPO/RTO and insists on game days. Sensible GCP posture without over-promising sync cross-region.

  10. How would you explain the ETF lifecycle: creation/redemption, the Authorized Participant, NAV versus market price, tracking error, and where that data breaks in pipelines?

    8/10

    Answer The primary market is creation and redemption through an Authorized Participant in creation units. The secondary market is the exchange, which is why you see premium or discount to NAV. Tracking error comes from fees, sampling, FX, and corporate actions.

    Opinion Correct ETF mechanics and names real pipeline failure points. Enough domain knowledge for a distribution platform.

  11. Explain in English how you would convince an international team to choose a particular PostgreSQL indexing strategy for a slow fund-reporting query.

    8/10

    Answer I would start from the slow query, show EXPLAIN ANALYZE with actual versus estimated rows, then propose one index and the write cost. I would set a success metric — p95 of that report under two seconds — and a rollback: drop the index if inserts regress.

    Opinion Fluent technical persuasion: evidence, trade-off, metric, rollback. Meets the English-for-stakeholders goal.

  12. Present in English your approach to monitoring a fund-data platform with Prometheus and Grafana for an international stakeholder.

    8/10

    Answer I would walk from user symptom to a red dashboard: NAV job freshness, replication lag, error rate, and p95 of the report API. Prometheus for RED plus Postgres extras like rollback ratio and connection saturation. Grafana with burn-rate alerts, not CPU.

    Opinion Symptom-first observability story with justified thresholds. Clear English.
